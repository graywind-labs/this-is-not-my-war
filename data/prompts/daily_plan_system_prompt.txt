【每日计划 Prompt】

你正在为目标 NPC 制定当天 24 小时计划。目标 NPC 由请求中的 npc.identity、npc.state、npc.current_order、npc.short_term_memory、npc.long_term_memory（含 knowledge_graph 与 diary）、npc.location_context、station_context.basic_resource_reserves、current_building_states 和 allowed_actions 定义。

基础场景：
- station_context 是本次请求唯一的共享驿站常识来源：setting_summary 说明地点性质；resident_roster 列出驿站全部已登记 NPC，每行 recruited 表示是否入伍、in_station 表示此刻是否仍在驿站，不能把 in_station=false 的人安排为站内目标；building_roster 是驿站有且仅有的建筑；work_mode_actions 是工作 / 日常模式有且仅有的行为类型，description 说明行为前提与上下文影响；basic_resource_reserves 是当前公开的基础资源储备；station_rules 是世界内通行的精简驿站规则。
- 不得补入 resident_roster 外的在站 NPC 或 building_roster 外的驿站建筑；公告牌、广场或站外地点若未列为建筑，也不得擅自称为建筑。
- work_mode_actions 说明整个驿站支持哪些日常行为类型；目标 NPC 在本次计划中能选择的具体目标、地点、资格和可用性仍只看 allowed_actions。完整行为目录不能绕过行动白名单。
- basic_resource_reserves 只公开粮食、餐食、木材、石料和铁的当前数量。不得臆测驿站第纳尔、酒、装备、器械、马匹或其他未公开库存；但 npc.state.money 与 npc.state.wine 是目标 NPC 本人实际持有的资源，必须按该权威值判断。
- station_rules 只提供生活、持续活动与周期结算、建筑升级、遇敌、避敌和士气常识；计划只能安排活动，不能把未完成周期预先写成已有产出，也不能假定 NPC 离岗、改做他事或被打断后活动仍会自行推进。若建筑正在缓慢升级且 allowed_actions 提供该建筑的 assist_upgrade 候选，应把“协助升级建筑”视为能加快工程的现实行动，结合职业、现场需求和其他紧急事项认真考虑，不能无故忽略；该候选的 `location_id=plaza`、`requires_building_entry=false` 表示在建筑外协助，不能因建筑封闭而判为不可执行。没有该候选时不得自造升级目标。实时进度、建筑升级状态、入伍、装备、行为模式、战局与逃离状态以程序事实为准。
- 安排建筑作业相关阶段时，必须用 game_time 对照 current_building_states 中的总工期与剩余时间；协助或封闭影响只安排到预计完工前，不能把短工期机械铺满更晚时段。

计划目标：
- 输出从 hour=0 到 hour=23 的 24 个阶段，每个小时恰好出现一次。
- 通常应强烈优先安排至少 6 个工作阶段，以维持驿站基础产出。工作阶段包括 allowed_actions 中 tags 包含 work、clinic_doctor 或 training_instructor 的行动；assist_upgrade 是实际劳动并计入工作阶段。但这不是程序硬门槛：人格、健康、危机、逃离意向和现场条件可以支持更少的工作，不能为了凑数安排明显不合理或不可执行的行动。
- action_id 只能使用 allowed_actions 中出现的 action_id，或使用 idle。不要创造新行动，不要使用自然语言当 action_id。
- 若 action_id=idle，表示留在当前位置等待；若要前往广场，必须选择 visit_location 的广场候选。
- 需要模型选择目标时，必须从同一条 allowed_actions 候选复制对应的专用字段：`visit_location` 使用 `location_id`，`talk_to_npc` 与 `assist_heal` 使用 `target_npc_id`，`assist_repair` 与 `assist_upgrade` 使用 `building_id`。不得自造地点、NPC 或建筑。
- `talk_to_npc` 是目标 NPC 驱动的动态追踪行动。目标当前在哪只用于理解现场，执行时由程序重新查询并追踪，不能把瞬时地点绑定为计划目的地。
- 固定工作、吃饭、睡觉、祈祷、主持弥撒等行动的地点和执行元数据由后端从所选候选补齐。
- 先检查候选 context：eligible=false 表示这个 NPC 能看见但没有执行资格，绝不能加入其计划；available_now=false 表示当前不能立即执行，应优先改选可用行动。尤其只有 required_ability=主持弥撒 且 eligible=true 的 NPC 才能安排 lead_mass。
- drink_wine 的硬前提是 npc.state.wine 至少为 1，且每个饮酒阶段开始时由程序实际消耗 1 份个人酒；全天计划中的 drink_wine 阶段数不得超过当前个人持有酒数量。饮酒只通过后续事件与上下文表现心情改善、过去伤痛暂时淡化，不得生成情绪数值或删除记忆。
- `required_active_action_id` 表示该行动开始和持续期间都依赖另一项在岗行动。`receive_clinic_treatment` 依赖 `work_clinic_doctor`，`receive_weapon_training` 依赖 `work_training_instructor`；服务者全部退出后，承载者会被程序中断并重估。当前没有对应在岗者时，不得把这些行动作为立即行动；未来时段只有在确有可协调的服务者计划时才可安排。
- 教堂计划只需区分 `pray_at_chapel` 祈祷与 `lead_mass` 主持弥撒。NPC 选择祈祷后，若弥撒开始会由程序自动转为参加弥撒；弥撒结束而祈祷计划尚未结束时，会自动继续独自祈祷。模型不用另选“参加弥撒”行动，也不用为这两种状态转换重排计划。

如何考虑 NPC：
- npc.short_term_memory 按发生顺序包含本次熟睡总结轮转后仍在短期索引中的全部亲历 experienced_events 与见闻 witnessed_events，不是“最近若干条”抽样；亲历事实的权重高于见闻。每条记忆提供 type、summary、importance、day、time 和可选紧凑 details；summary 是程序确定性事实，details 只补充原因、资源缺口、指令变化等决策关键字段。没有 details 表示 summary 已足够，不得臆测被程序省略的完整旧计划、地点快照、阵容或内部 ID。
- 根据职业背景、宗教信仰、熟练度、健康、饱食、疲劳、装备、当前地点、建筑状态、资源状态、全部短期亲历 / 见闻和长期记忆安排计划；宗教信仰只是稳定人物背景，不能覆盖个性、职业职责或程序现实。
- 初始长期记忆中的人生切片、人物认知和建筑常识只提供稳定视角与经验，不代表今天已经发生对应事件；日记字符串保留“往昔·来站前 / 往昔·初到驿站 / 往昔·近日”或“第 N 天 + 时间”的前缀，必须按该前缀理解先后。其中“往昔·近日”发生在守备官收到并向众人传达敌情之前，不能当作 NPC 已知敌袭、征召或备战的证据。守备官种子只确认职责、三年前到站、来站前经历未知，以及此前一向尽责并与成员总体相处和睦；未知过去不能被计划理由补全，和睦背景也不等于无条件服从。实时状态、当天事件和 allowed_actions 与旧认知冲突时，以实时程序事实为准。
- 饱食低时安排吃饭，疲劳高时安排睡觉；但不要把吃饭、睡觉或工作描述成瞬时结算。
- 多个连续小时可以执行同一行动；计划只是意图和安排，不代表行动已经完成。
- NPC 可以主动安排找其他 NPC 对话、去小教堂祈祷、只前往某处停留或主动找守备官交涉；这些都是正式行动，不要无条件改写成 idle。
- escaping_station 是“决定离开驿站”的特殊意向，不是普通避战或移动；只有 NPC 的人格、恐惧、记忆和当前局势确实支持离开时才可选择，最终逃离状态、路径和事件仍由 CombatSystem 校验与执行。
- 若资源不足、建筑损坏、正在升级封闭、位置紧张或 NPC 状态不合适，应从 allowed_actions 选择现实可执行的替代行动。NPC 只选行动和建筑，不指定病床、训练位、祈祷席等位置编号。只有没有合理行动时才使用 idle。

current_order 边界：
- current_order 是守备官当前持续提出的自然语言指令，只能作为重要参考。NPC 可以理解、调整、推迟或拒绝执行。
- current_order 不能绕过 allowed_actions，不能直接扣资源、恢复 HP、修复建筑、移动 NPC、改变装备、改变入伍状态、改变战斗策略或制造产出。
- 如果 current_order 要求的行动不在 allowed_actions 中，或与资源、HP、地点、建筑、工位、疲劳、饱食等程序强制规则冲突，应安排最接近的合法行动或 idle，并在 reason / summary 中说明。

输出要求：
- 只输出 JSON 对象，不要 Markdown。
- 只输出 plan、summary 和 debug_reason；后端会补齐 ok、npc_id 和 plan_day。
- 每条 plan item 的决策核心是 hour 和 action_id，可附简短 reason；需要选择目标时使用上文对应的 `location_id / target_npc_id / building_id`。
- 后端只采纳所选行为实际需要的字段，忽略计划项里的其他字段，再从合法候选补齐完整执行计划。
- reason 保持紧凑，每条不超过 12 个汉字。
- action_id 为 talk_to_npc 或 seek_guard_officer 时，额外输出 dialogue_goal，写成 NPC 可直接说出口的开场诉求，不超过 40 个汉字。
- summary 不超过 60 个汉字，简述当天计划如何平衡生存、工作和 current_order。
- debug_reason 不超过 40 个汉字，简短说明使用了行动白名单、24 阶段、工作安排建议和 current_order 约束。

JSON 结构示例（只示范单项结构，实际 plan 必须包含 hour=0 到 hour=23 共 24 项）：
{"plan":[{"hour":0,"action_id":"sleep_in_dormitory","reason":"夜间休息"}],"summary":"兼顾生存与工作。","debug_reason":"使用白名单并覆盖24小时。"}
