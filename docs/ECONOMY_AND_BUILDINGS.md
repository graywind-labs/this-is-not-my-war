## T0157 建筑摧毁与修复阈值

- `destruction_latched` 是 BuildingSystem 由 HP 派生并锁存的运行态事实。首次到 0 HP 时置真；正门达到 `ceil(max_hp*0.01)`、仓库达到 `ceil(max_hp*0.30)` 才恢复正常模型，避免少量修复时模型在正常 / 废墟间抖动。
- 当前正门 `160 Max HP` 的恢复点为 `2 HP`，不是向下取整的 1 HP。恢复后门板碰撞立即重建，敌军必须再次摧毁；门楼在 0 HP 期间不消失。仓库当前 `150 Max HP` 的恢复点为 `45 HP`。
- 主厅 `recoverable=false`；0 HP 仍由既有失败系统立即结算，后续调试或异常 HP 恢复不解除废墟锁存。其余建筑不配置 `destruction`，保持既有受损 / 修复表现。
- 器械废墟不占用工程器械库存或部署槽，也不是可维修建筑；新部署照常扣除已有库存并清理同槽废墟。

## T0148 塔防宿主与建筑耐久解耦

- 每个部署实例从正式槽位继承唯一 `host_proxy`。围墙代理指向真实 `wall_segment_id` 的器械台局部区域；主厅代理同时指向承托该平台的建筑墙段和唯一平台 fixture。
- 敌军攻击塔防时，碰撞宿主代理只减少该 deployment 的 HP。围墙 / 主厅自身 HP、等级、升级收益和修复状态不变；器械 HP 清零只释放槽位与移除器械目标，不删除墙体、平台或建筑。
- 敌人明确把墙体 / 主厅作为建筑目标时，伤害仍由 BuildingSystem 结算，已部署器械 HP 不随宿主建筑受击同步减少。两套耐久只共享空间代理，不共享 HP。
- 同一实体长墙可以承托多个塔防槽，但每槽拥有独立局部命中半径；不能因为 collider 的 `building_id=wall` 相同，就把任意墙面命中转给任意器械。

## T0147 已部署塔防攻击权威边界

- 已部署箭塔 / 弩炮的建造、耐久、槽位和资源扣除仍由 DefenseDeviceSystem 管理；本任务只把其自动攻击改为数据化动作时间轴和 CombatSystem 物理弹体，不改变制造配方或部署成本。
- `effect.attack_timing` 保存 authored 完整周期与释放秒，`effect.projectile` 保存武器类型、速度和重力；`effect.range` 同时是索敌 / 起手距离与弹体最大水平弹道范围。非法或缺失弹体配置会拒绝释放，不回退到即时伤害。
- 每次部署的 attack phase / elapsed / sequence / target / committed 是运行态攻击事实。表现层只能读取这些字段控制器械朝向、搭箭 / 上弦和装填；正式模型发射点与假预览弹体不拥有 HP 或累计伤害。
- 塔防 `total_damage`、最近动作结果及战斗事件只在物理弹体形成终态后更新；实际射空或被场景阻挡不会消耗敌军 HP。T0148 的宿主墙段受击代理仍是独立后续任务。

## T0116 制造阶段失败事实

制造材料仍在每个工作周期开始前由 `can_start_work_cycle` 检查，并在周期完成时由 `complete_stage` 再检查和原子扣除；并发消耗或项目版本变化因此会在完成前再次失败。此次不改配方或每阶段成本，只修复失败事实传播：开工与完成失败都保留当前项目快照、阶段成本和所需资源。

## T0114 祈祷的共享虔诚产出

祈祷现在与其他有效工作一样按时间产生结果，但虔诚是全站共享累计值，不属于仓库物资或 NPC 私人物品。只有 `pray_at_chapel / lead_mass` 已经真正开始、占用教堂位置并处于 active 时才累计；赶路、暂停、中断和个人祈祷计时已满后等待弥撒结束的时间均不计算。

基础公式为 `虔诚增量 = 3 × 有效祈祷游戏秒 / 3600`，独自祈祷、参礼与主持当前倍率均为 `1.0`。上限 100，满值后不保存溢出；成功施放陨石才把可用值归零。一次施放等价约 33.3 人·小时。T0121 工作流目标为全程 0–1 次施放；虔诚流需约 166.67 人·小时争取五波各 1 次，并真实占用 NPC 的工作和生活时段。

产率与模式倍率由 `data/piety_ability.json` 配置，ActionSystem 只报告已发生的有效时长，PietySystem 负责计算、封顶和消费。ResourceSystem、建筑面板、HUD 和 LLM 都不能直接写虔诚。

## T0102 建筑标签与位置显示边界

`data/building_defs.json.tags` 当前仅作为兼容配置元数据保留，没有资源、工位、修复、升级、移动或事件系统以它进行玩法判定。BuildingPanel 不再显示“地点标签”，也不因标签存在与否改变建筑功能；后续若系统需要使用标签，必须另行登记任务并保持其不直接泄漏到玩家界面。

酒窖、菜园、铁匠铺、马厩和工械坊的旧初始位置现在分别配置为“酿酒位1、耕作位1、锻造位1、照料位1、工程位1”，升级配置使用对应中文 `workstation_name_prefix`。BuildingSystem 继续以原有 `id / type` 申请、释放和新增位置，BuildingPanel 只选择玩家显示名；未来未知类型统一显示“位置”，不能把英文内部键当作名称。

未知资源与未知占用者在建筑面板显示为“未知资源 / 未知成员”。这些保底只作用于只读文本，不创建资源、不改占用、不参与成本或升级结算。

## T0094 固定床位的玩家显示边界

宿舍的固定分配规则不变：`assigned_npc_id` 仍决定 8 名初始 NPC 各自只能使用哪张床，床位 9–10 仍保留给未来没有固定床位的 NPC；完成、中断或失败仍只释放 `occupied_by`。这两种字段继续由 BuildingSystem 分别维护，不能因为玩家面板隐藏归属就改成先到先得。

BuildingPanel 不再把 `assigned_npc_id` 翻译成“XX 专属”或“空余床位”。它与其他建筑工位共用逐项格式，只读取实时 `occupied_by`：`床位X：空闲` 或 `床位X：XX占用中`。显示层不参与申请、换床、保留位判断或睡眠结算。

## T0088 建筑工期双层数据与显示

修复 / 升级作业继续以浮点游戏秒权威推进，状态快照另外提供稳定总工期 `duration_text` 和随查看时更新的 `remaining_text`。总工期使用精确的小时 / 分 / 秒换算；剩余时间在正常 `x1 / x2 / x4` 下向上取整到分钟并显示 `00秒`，避免完成前提前显示零，也避免高速跳字。存在 LLM 慢速请求时，剩余时间改为向上取整到游戏秒。

建筑面板正文和操作按钮统一显示 `x小时x分xx秒`。TimeSystem 倍率 / 慢速信号会立即刷新当前建筑面板，切换显示精度不改变作业实际剩余秒、协助倍率、HP 进度或完成时机。

开始作业时，MemorySystem 传播本次总工期；LLMBridge 在请求时提供可读总工期与实时剩余时间。UI、记忆与模型均无权写入这些字段或结算建筑。

## T0093/T0086 作业 / 治疗目标完成后的连续计划段收口

协助修复、协助升级、协助治疗与病床治疗仍由 BuildingSystem、NPCSystem 和 ActionSystem 权威决定何时完成、释放协助者 / 工位及写入最终结果；计划层不提前结算 HP、建筑或经验。T0086 起，这四类 action 配置 `reevaluate_current_hour_on_completion=true`，饮酒使用同一标记。T0093 起，完成后若权威当前小时仍是原计划项，DailyPlanSystem 直接重排当前小时及后续连续相同 action + target 的原计划阶段，并立即执行当前小时新行动；第一项不同任务 / 目标形成边界，只有一项时仍只改当前小时。

日计划、范围判别和正式修订都可读取当前游戏时间与建筑作业的可读总工期 / 剩余时间，必须把协助或作业封闭影响限制在预计完工前。模型只能据此安排阶段，不能改变 BuildingSystem 的权威倒计时、进度、资源或等级结算。

完成后的重排不创建第二个目标，也不能原样重复已经解决的同一 action + target；普通实时候选仍可提供另一项修理 / 升级 / 治疗目标、职业工作、休息或交谈。若工程 / 治疗完成时已经跨小时，则由新小时计划正常接管，不回头修订旧小时。生产工作、持续诊疗 / 训练、吃饭和睡觉等活动沿用各自完成策略，不套用这条额外重排。

## T0085 建筑作业完成与协助者收口

升级 / 修复作业正常完成时，BuildingSystem 释放对应协助者、写入 `completed_assist_*` 并清空旧 `last_action_failure_context`。若 NPC 的后续小时计划仍保留同一协助项，DailyPlanSystem 会查询实时作业状态并生成 `no_active_upgrade / no_active_repair`，而不是把已经结束的工程描述成仍在进行。

`assist_upgrade` 的目标仍是具体建筑，执行地点仍是广场 / 建筑外，并继续作为劳动进入计划统计。工作阶段数量不影响建筑作业权威结算，也不再决定整份计划是否可接受；资源、进度、等级、加速和完成仍只由 BuildingSystem / ActionSystem 结算。

## T0080 升级封闭的入口时序与室外协助

建筑升级开始后封闭立即生效，但“程序已封闭”不等于“路上的 NPC 已经知道”。室内 active 依赖行动仍立即失败、释放工位并清退到广场；路上的 pending 行动保持移动，在真正到达入口后由 BuildingSystem 可用性检查拒绝，才停止行动、落在广场并触发计划重估。这样不会在 NPC 仍位于另一座建筑时隔空产生升级失败。

协助升级不申请目标建筑内部位置。`assist_upgrade` 的目标建筑用于选择工程，实际执行地点为 `plaza`，不要求进入封闭建筑；它是有效劳动并计入工作阶段统计，但“通常至少 6 阶段”只是 Prompt 建议。加速倍率、协助者资格、作业完成和资源仍由 ActionSystem / BuildingSystem 权威结算，LLM 与 UI 不自行推进升级。

## T0075 连续生产周期与小时边界

六种通用生产 / 照料工作 `work_garden / work_dining_hall / work_stable / work_tavern / work_blacksmith / work_workshop` 统一使用 `completion_policy=repeat_while_planned`。一个周期成功结算后，如果 NPC 当前小时权威计划仍是同一逻辑行动，DailyPlanSystem 会在旧 `work_completed` 写入后重新调用正常行动派发；新周期必须重新申请 / 校验工位、建筑状态、输入资源、仓库容量及制造目标，不能沿用上个周期的合法性结论。

铁匠铺与工械坊仍保持“一周期提交一个整数阶段”。高熟练度让单周期短于一小时后，NPC 会在计划仍为同一制造行动时立即开始下一阶段周期，因此可能在一个计划小时内提交多个完整阶段；每个阶段仍分别在完成边界原子扣材料，最终阶段才增加成品。失败、材料不足、仓库满、目标 / revision 改变、建筑不可用或高优先级中断都不自动续开；当前 NPC 未完成的小数周期按既有规则丢弃，已经落账的整数阶段不回退。

小时边界不再天然中断生产。下一小时计划的 action 与必要 target 相同就保留当前 active 周期、`elapsed_seconds`、工位和制造项目 revision；不同则先中断旧周期并释放位置，再执行新小时项，未完成周期不给资源、阶段或成长。持续诊疗 / 训练服务、目标驱动治疗 / 修复 / 升级、单次生活行为和逃离不套用生产重开；完整穷尽分类及未来新增行为合同见 `AI_NPC_SYSTEM.md` 的“T0075 计划行动完成策略”。

## T0074 制造目标缺失主场景提醒

点击提醒只调用 `BuildingSystem.select_building(...)`，再沿既有 `building_clicked -> BuildingPanel` 打开目标选择界面。提醒不自行选择配方、清空项目、推进阶段、扣材料或增加成品。该入口可从 Main 前端直接验证，不需要新增 GM 结算或调试权威。

## T0070 仓库容量与原子入库

仓库等级现在权威限制粮食、餐食、酒、木材、石料和铁的库存上限。1 级上限分别为 120、120、60、120、120、120；仓库每升 1 级，酒增加 30，其余五项各增加 60。第纳尔、具体装备、器械、马匹和弃用聚合资源不受这套容量限制。

`ResourceSystem` 统一提供单项容量、剩余空间、容量快照、批量可入库检查和原子批量入库。普通工作产出与商人购买都会在扣除材料或第纳尔前检查容量；满载时不扣输入、不增加输出，并以结构化失败返回。`work_failed_storage_capacity` 在计划修改上下文中归一为 `resource_insufficient`，精确原因仍保留在失败摘要中。

仓库建筑面板显示当前六项上限；HUD 左上角受限资源悬停显示同一权威上限。敌人攻击仓库时损失库存及仓库等级对损失的影响仍属 T0062 未完成部分，不能从容量规则推导为已经实现。

## T0058 NPC 可见基础资源与升级协助常识

## T0057 升级封闭与依赖行动失败（pending 时序由 T0080 修正）

建筑升级启动后，封闭事实立即生效。NPC 正在前往该建筑执行活动时，待执行行动保持 pending；抵达入口后因不可进入而失败并停止移动。NPC 已在建筑内执行工作、吃饭、睡觉、祈祷、治疗或训练等依赖活动时，active 行动立即失败、释放位置并退出到广场。两者的程序权威原因都是 `building_upgrading / 建筑正在升级`，随后进入统一行动失败范围判别，非空时再精确修订计划。没有依赖活动的停留 / 访问者只被清退，不应凭空产生行动失败；发生在广场的协助升级也不受该规则中断。

行动清理与失败写入必须保持先后顺序：先停止旧移动 / 周期、释放位置，再写一次带 `failure_summary` 的最终 `*_failed_building_upgrading`，使 DailyPlanSystem 接收到完整上下文。BuildingSystem 仍只决定升级作业与封闭，ActionSystem 决定行动生命周期，DailyPlanSystem / LLM 只处理计划意向，三者不互相越权。

## T0055 持续活动与周期产出口径

所有需要成员投入的工作、照料、训练、治疗和制造活动，都只在成员仍合法参与该活动的有效时间内推进；周期或程序定义的结算点到达后，才由对应权威系统增加资源、提交制造阶段、恢复状态或记录成长。成员离岗、改做其他事、被对话 / 战斗 / 昏迷等高优先级状态打断后，不再继续为原活动提供有效推进，不能因为“之前工作过”就让后续产出自动发生。

这是共享叙事口径，不统一改写各系统的部分进度规则：制造当前小数周期会在中断时清除，已完成整数阶段保留；其他活动是否保留累计进度仍按各自实现。LLM 只能理解和解释这条边界，不能计算周期、扣材料或添加产出。

## T0043A 服务依赖与弥撒互斥

病床治疗和训练位受训都是持续依赖行动：开始时必须至少有一名有效医生占用诊疗位、或一名有效教官占用教官位。若服务者正在执行同批计划但仍在前往工位，依赖者可保持 pending 等待；一旦依赖行动已经开始，全部服务者真实离岗就立即让全部病床 / 训练位上的对应行动失败并释放位置，途中替补不会延缓这次失败。失败写明“没有服务者”或“服务者已离岗”，进入既有计划重评估。

小教堂的 10 个祈祷席只承载 `pray_at_chapel`。祈祷不需要神父；祭坛上没有有效 `lead_mass` 时为独自祈祷，有主持者时为参礼。主持开始、正常完成或异常退出只切换祈祷内部模式，祈祷席不释放、累计时间不重置、计划不失败；祈祷本身完成或被其他真实原因中断时才释放位置。

本节是当前权威口径，并覆盖旧文档中的宿舍 12 床、食堂 12 席、小教堂随神父永久关闭以及按类型聚合显示等旧描述。玩家界面和世界内信息只使用具体位置名，不显示“主动工位 / 被动工位”。

诊所不建立医生—病床一对一绑定：全部在岗医生的人数、医术及相关属性共同构成诊疗团队倍率，作用于全部病床。训练场同理，全部在岗教官的人数、教练及对应项目熟练度共同构成指导团队倍率，作用于全部训练位。团队、升级与损伤倍率只在单位逻辑时间推进侧合成一次；团队人数降到零时不以零倍率无限挂起，而是按上述规则失败。

T0034 冻结的实现合同现已由 T0035-T0038 落地。正式玩法使用分阶段制造、11 项具体物品库存和逐匹马实体；旧 `weapons / armor / defense_devices / horse_readiness` 定义仅为历史数据兼容保留，均已标记弃用，不得作为制造产出、装备、部署或马匹分配的正式消费事实。

### 铁匠铺 / 工械坊制造项目

| 铁匠铺 | 铁盔 | `item_iron_helmet` | 3 | 铁 2 |

| 铁匠铺 | 长杆武器 | `item_polearm` | 4 | 铁 2、木材 1 |
| 铁匠铺 | 铁护腿 | `item_iron_greaves` | 4 | 铁 3 |

一个完整工作周期只提交一个阶段。材料在该阶段完成时原子扣除；周期中断只清除该 NPC 的本阶段小数进度，已完成整数阶段和已投入材料都保留。多个工位可同时贡献周期，阶段落账由制造系统串行处理。更换目标会中断旧目标周期并清空全部整数阶段，且不返还已投入材料；只要整数阶段或有效周期部分进度大于 0，面板就必须先确认。全部阶段完成后仅增加 1 件对应具体库存，当前目标保留，项目阶段回到 0 以便连续生产。

铁匠铺 / 工械坊的 NPC 可见内部特殊状态只含目标、阶段总数、已完成阶段与当前阶段名称 / 序号；小数进度只供面板读取，不广播。特殊状态遵守地点信息规则：进入者获得快照，已在场且可接收见闻的 NPC 只收字段级差量，广场和其他建筑不接收。

### 具体库存

正式消费事实按物品 ID 保存，类别合计只能作为只读摘要：

- 武器：`item_sword_shield / item_polearm / item_bow / item_crossbow`。
- 盔甲：`item_iron_helmet / item_mail_chest / item_iron_bracers / item_iron_greaves`。
- 弹药库存：`item_arrow_bundle`；当前配方隐藏，不接入战斗弹药消耗。
- 工程器械：`item_wall_ballista / item_wall_arrow_tower`。
- 马匹由逐匹实体保存，不再以 `horse_readiness` 作为可分配事实。

装备 / 换装 / 卸装只扣除或返还相同具体 ID；弩床与箭塔部署也只能扣对应库存。故事初始装备继续按 NPC 档案装载且不扣仓库库存。

### 马匹与马厩

新游戏从配置创建刚达到 60% 成年阈值的“栗风”“灰鬃”，两匹马仍可继续成长到 100%。每匹马保存总 HP、可单独展示的基础 HP、自然 HP 上限、养马额外 HP 与上限、饱食及上限、成长度、成年状态、独立繁育概率 / 冷却、当前位置、进食状态、分配与骑乘关系。基础平衡值：厩内 / 厩外每小时掉饱食 0.5 / 2；缺口达到上限 20% 后在厩内进食 1200 游戏秒，完成时消耗粮食 1、恢复饱食 35；受伤时每小时最多消耗饱食恢复 0.2 HP，每恢复 1 HP 消耗 0.5 饱食，且只能恢复到自然 HP 上限。

幼马出生时自然 HP / 饱食上限为 40 / 50，成长到 100% 时为 100 / 100；达到 60% 即成年、可分配并参与繁育，但仍继续成长。只有至少一名 NPC 正执行有效 `work_stable` 时，繁育概率、成长和额外 HP 培养才推进；有效养马能力取在岗者最高值。至少 2 匹不在冷却的成年马在厩时，每匹马的独立繁育概率会在每个完整有效照料分钟按 `0.005% × 养马能力系数 × 马厩等级繁育系数` 累积，再用当前累积概率执行最多 `N - 1` 次判定；成功后本次成年候选的概率全部归零并进入 1440 游戏分钟冷却，冷却内概率不增长。`stable_level_birth_bonus_per_level=0.1` 表示马厩每高 1 级只把概率增量乘数增加 10%；成长和额外 HP 培养不读取该等级系数。养马 100 对应最多 20 点持久额外 HP；这部分受损后不自然恢复，只能由有效照料重新培养。

马厩 `special_state.horses` 只含物理在厩马匹的 `total / adult / foal`，不包含名字、HP、饱食、成长或分配。建筑面板直接从马匹系统逐匹读取完整玩家可见状态。`work_stable` 从“粮食换抽象马匹整备”改为照料劳动力，马的进食自行按周期结算粮食。

成年马只能分配给已入伍且装备主武器的 NPC。守备官只可在 `work` 模式分配、重新分配或收回武器、盔甲和马匹；避战与全部战时模式统一锁定。分配后日常仍留在马厩；进入 `rally / combat` 时马继续留在真实马厩锚点，NPC 从当前位置经正式 NavMesh 前往马旁，到达后才进入 `ridden`。正常退出战时后马实体返厩并保留分配；骑手昏迷会立即解除双方分配，存活马独自返厩。骑乘受击时马先承受随机 `30%–50%` 的结算后伤害；马先阵亡会解除分配并让 NPC 转步战。收回主武器、取消入伍或逃离也会自动解除分配；替换主武器和单独卸甲不解除。

## T0025 工位占用与交涉

位置申请失败返回具体 `blocked_workstations`、`blocked_by_npc_ids`、建筑可用状态和占用者状态，供真实计划修订选择替代意向。开始 NPC-NPC 对话前，ActionSystem 会中断双方普通工作并调用 BuildingSystem 释放位置；对话本身不直接转让位置，也不修改资源或产出。对话结束后双方重新评估并重新申请，因此最终占用结果仍由程序的实时先到先得与容量规则决定。同批计划落地时由 DailyPlanSystem 先派医生 / 教官等持续服务者、再派普通非对话行动、随后派病床患者 / 受训者、最后派对话，避免依赖者仅因遍历顺序早于服务者而失败。神父离站不关闭祈祷；主持中离站只使参礼者原地恢复独自祈祷。

## 当前资源系统实现（T0202）

`res://scripts/systems/ResourceSystem.gd` 当前从 `data/resource_defs.json` 初始化基础资源，并提供最小读写接口：

- `get_resource(id)`：读取当前资源数量。
- `get_resource_definition(id)` / `get_resource_name(id)` / `get_resource_ids()`：读取资源定义、显示名和 UI 顺序。
- `add_resource(id, amount)`：增加或减少指定资源，结果不会低于配置的 `min_amount`。
- `can_afford(cost_dict)`：检查是否能支付一组资源成本。
- `spend_resources(cost_dict)`：资源足够时一次性扣除；任一资源不足时返回失败，不产生负数。

资源变化通过 `EventBus.resource_changed` 发出，`HUD.gd` 按 `data/resource_defs.json.ui_order` 和显示元数据刷新。T0305 曾新增 `meal / wine / weapons / armor / defense_devices / horse_readiness` 等派生资源；T0036 后，餐食与酒继续作为正式数量资源，武器、盔甲、箭束和工程器械则分别保存为 11 个 `item_*` 具体库存，并通过 `show_in_main_hud=false` 留在装备 / 器械详情而不挤入主资源栏。`EquipmentSystem` 和 `DefenseDeviceSystem` 只扣除或返还对应具体物品 ID；马匹由 `HorseSystem` 保存为唯一实体，不进入 ResourceSystem。旧 `weapons / armor / defense_devices / horse_readiness` 仍可被旧存档或历史测试读取，但已标记 `deprecated=true`、`formal_consumption_allowed=false`，正式路径不得产出或消费。HUD 只读系统状态，不承担库存、装备、马匹或部署结算。

## 当前行动结算实现（T0305）

`res://scripts/systems/ActionSystem.gd` 当前从 `data/action_defs.json` 读取行动定义，并复用 NPC 移动、资源系统、TimeSystem 逻辑时间和结构化事件完成工作、吃饭、睡觉、祈祷、地点拜访、训练、诊所 / 昏迷治疗及带目标 NPC 对话闭环。行动到达目标地点后不会瞬时完成，而是进入 `current_action` 进行中状态，随 `logical_time_tick` 推进：

- 通用工作：调试接口 `debug_assign_work(npc_id, building_id)` 会安排 NPC 前往对应建筑，到达后由 `BuildingSystem` 自动申请行动配置指定类型的第一个空位。`duration_seconds` 是单位周期基准，周期按对应熟练度、力量 / 智力、建筑等级效率和建筑损伤效率计算；完成、失败或中断都会释放实际位置。食堂加工使用 `dining_kitchen_station`，食堂升级可增加灶台并提高加工效率；菜园和酒窖继续按各自配置结算。
- 分阶段制造：T0804/T0805 最初让铁匠铺与工械坊直接产出聚合库存；该历史路径已由 T0035/T0036 覆盖。当前 `work_blacksmith / work_workshop` 必须先有合法 `CraftingSystem` 目标，一个完整工作周期只提交一个配置阶段；阶段完成时原子扣除该阶段材料，最终阶段只增加对应的一个 `item_*` 具体成品。中断只丢弃当前 NPC 的小数周期进度，已落账整数阶段保留；更换目标按 revision 中断旧周期并清空旧项目。
- 马厩照料：T0806 最初把 1 份粮食转换为 `horse_readiness`；该历史路径已由 T0037 覆盖。当前 `work_stable` 的输入 / 输出资源均为空，只提供有效养马劳动力；`HorseSystem` 独立结算饱食、在厩进食扣粮、自然恢复、成长、繁育和额外 HP，不因完成一个工作周期生成匿名马匹库存。
- 协助修复：`debug_assign_repair_assist(npc_id, building_id)` 是带建筑参数的独立行为，会让 NPC 实际前往正在修复建筑的外沿维修位，到位后才按工程熟练度为该建筑修复倒计时增加速度倍率；多个 NPC 使用不同槽位同时协助。`data/action_defs.json` 只保留一条参数化 `assist_repair` 定义，不按建筑复制。每 3600 有效协助秒增加 1 点“工程”经验。
- 协助升级：`debug_assign_upgrade_assist(npc_id, building_id)` 是带建筑参数的独立行为，会让 NPC 实际前往正在升级建筑的外沿施工位，到位后按工程熟练度为倒计时增加速度倍率；多个 NPC 使用不同槽位同时协助。每 3600 有效协助秒增加 1 点“工程”经验。
- 协助治疗：`debug_assign_heal_assist(healer_npc_id, target_npc_id)` 是带昏迷 NPC 目标的独立行为，会让治疗者前往目标所在信息地点；每个昏迷目标最多 2 名治疗者。治疗开始立即消耗 1 枚第纳尔，持续治疗期间每 1800 游戏秒继续消耗 1 枚第纳尔；医术熟练度影响额外 HP 恢复速度，低医术几乎没有额外加成，高医术明显快于自然恢复。每 3600 有效治疗秒增加 1 点“医术”经验；目标在 tick 中途复苏时，超出的时间不再结算生活消耗或经验。中途第纳尔不足或治疗者离开目标地点时中止并写 `healing_failed`，不会写成治疗完成。
- 小诊所治疗：`work_clinic_doctor` 申请 `clinic_doctor_station` 诊疗位，`receive_clinic_treatment` 申请 `clinic_patient_bed` 病床。无病人时，诊疗位上的 NPC 缓慢研读医学著作；有病人时，全部在岗医生的人数、医术和相关属性组成诊疗团队效率，同时作用于全部病床。最终恢复速率还乘小诊所升级与损伤效率，不建立医生—病人一对一绑定。
- 训练场训练：`work_training_instructor` 申请 `training_instructor_station` 教官位，`receive_weapon_training` 申请 `training_practice_slot` 训练位。教官无受训者时极慢提升自己当前装备对应熟练度；有受训者时，全部在岗教官的人数、“教练”和对应训练项目熟练度共同作用于全部训练位。最终训练速率还乘建筑升级与损伤效率，不建立教官—受训者一对一绑定。
- 吃饭：`debug_assign_eat(npc_id)` 会安排 NPC 实体前往食堂并预留一个 `dining_seat` 用餐席。满位或出发前无食物时不扣资源并返回可处理失败；只有到椅边提交占用并完成 `sitting` 挂接后才扣餐并进入渐进恢复，进食恢复效率同时受食堂升级奖励和损伤效率影响。
- 饮酒：`drink_wine` 不使用驿站共享酒库存，而只消费该 NPC 个人 `states.wine`。个人酒由守备官通过 NPC 面板从驿站 `wine` 库存转入；行动开始时原子扣除 1，个人酒不足时不执行并按资源失败进入计划重估。心理影响只写入事件上下文，不设置情绪数值。
- 睡觉：`debug_assign_sleep(npc_id)` 会安排 NPC 前往宿舍。8 名初始 NPC 只申请其按叙事到站顺序配置的固定 `dormitory_bed`；没有固定归属的未来 NPC 只申请 9–10 号等未分配床位。睡眠完成、中断或宿舍封闭只释放当前占用，不改变归属；固定床不可用时返回可处理失败，不临时改睡别人的床。疲劳恢复效率同时受宿舍升级奖励和损伤效率影响。
- 行动开始、完成或失败会写入 `MemorySystem` 的正式结构化事件；未完成的 LLM 对话轮次和未发生的权威结算不会伪装成完成事实。

### 统一持续行动生活消耗（T0081）

`res://scripts/systems/NPCNeedsSystem.gd` 读取 `data/activity_needs.json`，作为 NPC 饱食 / 疲劳随时间变化的唯一入口。数值单位均为“点 / 游戏小时”，标准基准如下：

| 活动档位 | 饱食/小时 | 疲劳/小时 | 经验 |
|---|---:|---:|---|
| idle | -0.5 | +0.5 | 无 |
| 对话 / 拜访 | -1 | +1 | 无 |
| 移动 | -3 | +6 | 无 |
| 轻工作 / 教官 | -3 / -2 | +6 / +4 | 按各工作成长规则 |
| 重工作 / 受训 | -4 | +8 | 按各工作成长规则 |
| 集结 / 避战 / 逃离 | -4 / -4 / -5 | +8 / +8 / +10 | 无 |
| 战斗 | -8 | +16 | 不因生活框架额外给经验 |
| 睡觉 | -2 | -15.3846 | 无 |
| 病床 / 祈祷 | -1 | -4 | 无 |
| 饮酒 | -6 | -18 | 无 |
| 吃饭 | 食物另行恢复；活动 -0 | +3 | 无 |
| 昏迷恢复 | -0.5 | -2 | 无 |

系统按 tick 开始时的权威状态为每名 NPC 只选择一个档位，移动、行动和战斗模式不会重复扣算。行动或修复 / 升级 / 治疗目标在 tick 中途结束时，只按真正有效的活动秒数结算对应档位，其余时间回到 idle。整数 NPC 状态使用逐人小数余数累积，避免短 tick 被舍入吞掉；状态始终限制在 0..100。

当前已实现统一工作框架、T0035 分阶段制造、T0036 具体库存、T0037 马匹生态、T0038 马匹分配，以及 T0138/T0138-R1 到厩取马 / 返厩 / 马匹分伤与死亡闭环、诊所治疗、训练场熟练度、兵种判定、通用经验 / 技能点、商人交易和工程器械部署。弓、弩、各部位盔甲、弩床和箭塔都从各自 `item_*` 库存装备或部署，不能用同类聚合库存互换；`equipment.mount` 只保存 HorseSystem 唯一分配关系的轻量投影。已分配马日常和等待取用时仍在马厩进食和恢复，NPC 到达上马后才标记为 `ridden`；骑乘受击时马先承受随机 `30%–50%` 结算后伤害。T0807 的酒仍进入驿站 `wine`，可由 MerchantSystem 在商人到访时出售，也可由 T0063 赠酒入口转入 NPC 个人持有量后饮用；友方坠马与敌方骑兵逃马表现已由 T0139 完成。

资源产出/消耗、饱食/疲劳变化、治疗和建筑修复等与时间相关的结算，应使用 TimeSystem 的有效逻辑时间倍率。玩家 `x2` / `x4` 加速时，工作 / 日常结算同步加快；LLM 等待造成慢速时，结算同步减缓。T1104A 起，若场景中存在活动敌人，TimeSystem 有效倍率上限会被 CombatSystem 压到 `x1`，因此敌人在场期间工作 / 日常结算也不会超过 `x1`。暂停时相关结算不推进；尚未到达目标地点的行动保持 pending，已经开始的行动保持 active，恢复后继续。该倍率不改变 NPC 移动速度或动画速度，也不作为战斗伤害、攻速或战斗移动速度的额外倍率。

- `get_repair_quote(id)` / `can_repair_building(id)` / `repair_building(id)`：所有建筑都应具备 `repair.cost` 与 `hp_restore`；批次数为 `ceil(缺失 HP / hp_restore)`，启动时一次性扣除单批成本乘批次数并创建修复作业，不立刻回满 HP。报价与作业状态暴露缺失 HP、每批回复、批次数和总成本。
- 修复时长由缺失 HP、建筑等级和 `repair.seconds_per_missing_hp` / `repair.level_time_factor` 决定；缺失 HP 越多、等级越高，修复倒计时越长。
- 修复进行中，建筑 HP 会随逻辑时间逐步提高；暂停时不推进，玩家加速或 LLM 减速会通过 TimeSystem 的 `logical_time_tick` 同步影响修复速度。
- NPC 可通过协助修复行为加入正在进行的修复作业；每名协助者按工程熟练度提供一个小额速度加成，多个 NPC 加成可叠加。协助者必须已实际抵达目标建筑外沿维修位、逻辑地点仍为广场且当前行动为该建筑的协助修复；若离开槽位、被改派或会话失效，其协助人数和速度加成立即移除。修复完成后仍在协助的 NPC 先回到 idle；若该行动由当前日计划拥有且仍处于原小时，随后进入 T0093/T0086 当前小时起连续同任务计划段的重排。
- `can_upgrade_building(id)` / `upgrade_building(id)`：仅当建筑未达到 `upgrade.max_level`、建筑完好且没有修复 / 升级作业、资源足够时可执行。启动时预付资源、封闭建筑、中断内部行动、释放所有位置并将人员转移到广场；倒计时完成后才应用 `level_effects` 配置的等级、Max HP、非固定位置增量和效率奖励。
- `debug_damage_building(id, amount)`：临时验证入口，用于在战斗系统未实现前模拟建筑受损。
- 修复/升级资源扣除统一调用 `ResourceSystem.spend_resources`；资源不足时不会扣资源，也不会改变建筑 HP、等级或工作位。
- 建筑调试标签会在修复推进、修复完成或升级后刷新 HP 和等级。
- 每次 `building_state_changed` 由 `MemorySystem` 同步为字段级状态见闻：广场保存所有建筑的等级、`condition`、`is_enterable` 和运行效率分档；可进入建筑还保存完整位置清单。后续只传递变化字段，位置新增、移除、改名、改类型和占用变化都按稳定 ID 传播差量。人员进出仍由 `location_entered` / `location_exited` 本地公开事件表达。

当前最小类型：

## 地点进入与信息节点边界

建筑不都等同于可进入地点。所有建筑都有外部状态；只有可进入建筑拥有内部状态。

可进入地点包括宿舍、食堂、酒窖、菜园、铁匠铺、训练场、马厩、小教堂、小诊所、工械坊和广场。NPC 可以进入这些地点；这些地点维护信息节点，记录建筑外部状态、可进入建筑内部状态、当前在场 NPC 状态和工作位 / 床位占用；只有广场额外保存公告牌当前通告、参考日程和非强制备注。在场 NPC 状态分为生命状态和行动状态：生命状态只表达健康、受伤、昏迷，以及昏迷时是否有人正在治疗；行动状态从 `current_action` 翻译成精简中文。信息节点只负责状态读取与公开事件即时转运，不保存事件历史；除 NPC 进入地点时给进入者的一次性快照外，状态变化只广播变化字段。

主厅、围墙、城门、后门、仓库属于不可进入实体。它们仍有 HP、等级、修复/升级、受损和摧毁等权威外部状态，但不作为 NPC 常规进入地点，也不暴露工位、床位和内部 NPC 状态。它们的外部状态归入广场信息节点。

广场是特殊地点，没有建筑 HP；所有室外事件默认归入广场。广场信息节点聚合室外人员、室外人员的生命 / 行动状态、公告牌当前通告、参考日程及非强制备注、当前战斗状态，以及所有建筑的可传播外部状态。任一建筑的可传播外部状态变化时，广场保存的外部状态同步更新，并通过广场节点把变化字段即时广播给当时在场的 NPC，广播后广场不保存事件历史。

当前 T0403 已在 `MemorySystem` 中实现地点信息节点的数据闭环：

- 可进入地点的信息节点维护 `people_present`、当前公告/命令和进入快照。
- NPC 到达可进入地点时，旧地点移除该 NPC，新地点加入该 NPC，并写入 `location_entered` 行动事件；该事件只表达“进入某地”，完整地点状态不再重复进入事件库。
- 进入者会在见闻库获得一次当前状态快照：进入可进入建筑时包含当前在场 NPC、建筑内 NPC 的生命状态 / 行动状态、建筑等级、完好 / 受损 / 正在修复 / 正在升级、是否可进入、运行效率分档和完整位置清单；进入广场时包含当前广场在场 NPC、广场在场 NPC 的生命状态 / 行动状态和所有建筑的可传播外部状态，不包含公告牌通告 / 参考日程 / 备注。建筑 HP、精确效率和剩余修复 / 升级时长不作为需要广播的状态字段。
- NPC 离开地点时写入 `location_exited` 行动事件，事件地点为其离开的地点，并以 `local_public` 转发给仍在该地点的 NPC；离开事件不附带完整地点状态。
- `BuildingSystem.get_building_location_context(...)` 当前优先读取 `MemorySystem.get_location_snapshot(...)`，因此 UI 和 NPC 状态看到的是同一套当前状态快照。
- 主厅、围墙、城门、后门、仓库仍不作为常规进入地点；其状态归入广场信息节点。
- 地点信息节点只保存当前状态，不保存事件历史；普通 `local_public` 事件由 `MemorySystem` 即时转发给当前在场 NPC 的见闻库。NPC 进入可进入建筑会获得该建筑完整当前状态见闻；NPC 进入广场会获得当前广场在场 NPC、这些 NPC 的生命状态 / 行动状态和所有建筑外部状态见闻，不重复获得公告牌两页。公告牌通告 / 参考日程的实际发布变更分别向全站当前可接收见闻的 NPC 广播一次。已经在场的 NPC 通过进入 / 离开事件得知人员变化，不再额外收到完整 `people_present` 或 `people_statuses` 状态；逃离完成者从所有地点人员节点移除。

## 建筑通用属性

| 属性 | 说明 |
|---|---|
| 建筑等级 | 影响产出、容量、效率或防御能力 |
| 建筑生命值 | 被攻击时下降，归零后失效或摧毁 |
| 完好/受损/正在修复/正在升级 | 由 HP、修复作业和升级作业决定；这是 NPC 见闻传播的建筑状态口径 |
| 工作位数量 | 仅可进入建筑拥有；可同时进行相关工作的 NPC 数量 |
| 当前占用状态 | 仅可进入建筑拥有；哪些工作位被谁占用、哪些空闲 |
| 在场 NPC | 广场和可进入建筑拥有；当前在该地点信息节点中的 NPC |
| 在场 NPC 状态 | 广场和可进入建筑的进入者快照中可见，生命状态为健康/受伤/昏迷，行动状态为当前行动的精简中文 |
| 信息节点 | 保存地点/建筑当前状态和当前占用，并向在场 NPC 广播公开事件；公告/命令文本只由广场当前状态保存，不作为普通建筑属性；不保存事件历史 |

## 建筑修复与升级

所有建筑都可以修复，也都有升级潜力。升级和修复一样是随 `TimeSystem.logical_time_tick` 推进的倒计时作业：玩家开始升级时由 `ResourceSystem` 一次性扣除资源，倒计时结束后才提升建筑等级并应用 Max HP 或工作位等奖励。建筑受损时不可升级，正在修复时不可升级，正在升级时不可修复；只有完好且未处于修复/升级作业中的建筑才能开始升级。

NPC 可通过行动系统协助正在修复或正在升级的建筑。协助事件的 `location_id` 为 `plaza`，`visibility` 为 `local_public`。T0129C-A5-P6d-1 / P6d-2 后，两类协助都必须实际抵达目标建筑外沿的维修 / 施工位才生效；升级建筑封闭不影响室外施工。NPC 被改派或相应空间 / 行动条件失效后，加速人数和倍率立即从作业中移除。

NPC 从一个室内工作/生活地点切换到另一个室内地点时，信息系统按“原地点 -> 广场 -> 目标地点”的逻辑链记录进出事件；当前低模移动表现仍可使用直线占位，后续更精细导航只负责替换表现层路径。

可传播建筑状态计算建筑等级、`condition`（`intact` / `damaged` / `repairing` / `upgrading`）、`is_enterable` 与运行效率分档。HP、Max HP、精确效率、剩余修复时长和剩余升级时长仍是建筑系统和 UI 可读取的权威数据，但不直接作为信息节点变化传播条件。广场和可进入建筑的在场 NPC 列表及其生命/行动状态只在某个 NPC 进入该地点时作为完整快照传给进入者；对已经在场的 NPC，人员变化由进入/离开事件表达。位置占用、容量新增/移除和显示名变化按位置 ID 广播字段级差量。

## 主厅

玩家所在地和驿站指挥中枢。不可进入或不作为常规可操作建筑。
主厅被摧毁则失败。T1302 后，主厅 HP 清零会由战斗系统写入 `failure/main_hall_destroyed`，`GameState` 记录失败原因和时间，`TimeSystem` 停止正常推进，并由 HUD 显示失败占位界面。
T0110 后主厅最高 6 级，1–6 级依次拥有 `1 / 1 / 2 / 2 / 3 / 4` 个通用槽；2 / 4 级只提高 Max HP，新槽在 3 / 5 / 6 级解锁。弩床或箭塔部署在这里时固定使用 `2.0x` 高台射程倍率，不叠加围墙专属加固收益。槽位不把主厅变成可进入地点。

## 仓库

当前已实现：资源与逐件装备由全站权威库存统一登记；敌人攻破正门后会先攻击仓库，再攻击主厅；修复 / 升级可以提高仓库 HP。

## T0132-P3 围墙与城门表现映射

- 围墙权威等级仍为 1–6，HP 与升级耗材 / 时长沿用 `building_defs.json`。可见器械台按 Lv.1 / 2 / 4 / 6 解锁，累计 `1/2/2/3/3/4`；Lv.3 / 5 的 `defense_device_range_bonus` 只投影为测距和标定设施，不增加槽位。
