# CODING_RULES.md

## 总原则

代码必须服务于最小可运行闭环。  
优先清晰、稳定、可调试，而不是炫技。

## Godot / GDScript 规则

路径规则：项目规范路径为 `D:/这不是我的战争/`，`D:/MyGames/这不是我的战争/` 是指向它的 NTFS Junction。工具输出比较必须先解析 Junction / 最终目标，不得以未经规范化的路径字符串判断工程身份。

1. 一个脚本只负责一个明确模块。
2. 系统之间通过 EventBus 或显式接口通信。
3. 不在 `_process` 里做高成本逻辑，除非必要。
4. 需要定时的逻辑尽量由 TimeSystem 驱动。
5. 外部配置必须可缺省、可校验、出错可提示。
6. 所有 JSON 字段读取要有默认值，避免空字段崩溃。
7. 对 LLM 返回 JSON 必须做合法性检查。
8. 重要状态变化必须写入事件日志。
9. UI 不直接决定权威结果，只触发系统请求。
10. 不把 API Key、私密配置、模型地址硬编码进脚本。
11. 结构化事件必须通过 MemorySystem 统一写入；不要让各系统各自维护互不兼容的事件数组。
12. 事件库和见闻库分开保存：亲历事件写入 NPC 事件库；公开事件、状态广播和公告由地点/广场节点即时转发给当前在场 NPC 后写入接收者见闻库。地点/建筑节点不保存事件历史，NPC 进入地点不继承过去事件。
13. 事件 summary 必须按事件类型模板确定性生成，不调用 LLM，也不要试图用通用主宾语规则生成所有事件句子。
14. 事件、测试夹具与文档样例中涉及已定义的人物、马匹、建筑、敌人、武器和防御器械专名时，必须使用对应 `data/*.json` 正式定义；自动化夹具应优先直接读取正式定义或显式校验 ID 与显示名，禁止为方便测试临时编造专名。
15. 调整 3D 模型、附件或道具的 Transform 后，自动化数值通过只是必要条件；必须运行实际场景并至少检查正面、侧面截图，动作附件还要覆盖能暴露问题的代表相位。验收须按常理检查持握部位、穿模、正反方向、接地与重心，明显不合理时继续调整，不能用错误采样点或单一数值收口。
16. 校准导入武器或工具前，必须先读取真实网格 AABB、顶点或明确的握点 / 工作端标记，确认模型局部轴哪一端才是剑尖、刃口或工具头；不得凭外观印象、欧拉角正负或错误采样点猜方向。挂在 `BoneAttachment3D` 下的附件会继承不同角色、动画和加载路径的手骨基底；需要跨骨架保持稳定朝向时，应以角色可见前向和世界 Up / Right 构造目标全局 Basis，再把真实握点对齐手掌，不能只反复试局部 `rotation_degrees`。自动化至少断言工作端相对握点的世界高度、角色前向点积和握点距离，并复核正面、侧面及代表动作相位截图；任一断言失败或截图仍不合常理时，不得声称完成。
17. 世界 / 角色空间的附件姿态校准只负责定义待机、收纳或持握基准，不能在需要骨骼驱动的攻击、工作或训练动作中逐帧覆盖附件的全局 Transform。进入动作前应保留已验收的附件—手骨局部 Transform，动作期间由 `BoneAttachment3D` 随手骨完整移动和旋转；只有确实需要独立瞄准或双手约束的道具才允许动作期重算，并须有专用逻辑。自动化不能只断言附件父节点名称，还必须采样动作代表相位，验证手掌实际位移、附件实际位移和二者运动方向一致。
18. 骑乘动作优先复用已经验收的步战上半身：以稳定跨坐片段作为全身基底，只替换 Spine、Chest、Neck、Head、肩、臂和手等上半身骨轨，Hips 与腿保持骑乘基线。若源步战片段把瞄准 / 构图旋转写在 Hips，必须把 `foot_hips * foot_spine` 的合成结果转移到骑乘 Spine，不能直接动画骑乘 Hips，否则会同时扭歪上身和跨坐腿。前倾应作为 Spine 上的有界附加旋转，并用侧面截图确认方向。
19. 程序化附件必须为每个模型记录真实局部轴和源握点，位置统一按“目标手掌点减去当前 Basis 变换后的源握点”反算。不要把模型原点、AABB 中心或镜头中的左右当成握点；“NPC 的右手”始终按角色自身左右定义。剑刃、长杆、弓、弩和工具工作端的方向约定应写在代码常量旁，并由快照验证。
20. 复合动作验收至少采样开始、蓄力 / 中段、命中 / 释放和还原阶段；同时比较对应步战与骑乘上半身的关键骨轨、武器—手掌局部关系、骑乘腿姿和人物—马匹前向。模型调整后必须查看实际渲染截图，不能因 headless 断言或父节点正确就宣称完成。临时抓图脚本和图片验收后清理，不把一次性截图资产长期堆入仓库。

## Python 后端规则

1. 所有接口返回 JSON。
2. 所有 LLM 输出都要校验。
3. 模型供应商通过 Model Adapter 隔离。
4. Prompt 模板放在 `data/prompts/` 或后端模板目录，不要散落在业务代码中。
5. 必须记录 token 和调用用途。
6. 请求失败必须返回可处理错误，不让 Godot 卡死。
7. 所有外部 Key 使用环境变量。
8. 不把用户游戏存档和开发配置混在一起。
9. Mock provider 只能作为开发期显式配置或调试接口使用；成品 / Demo 真实 provider 失败时不得自动返回 mock 内容伪装成功。
10. 模型调用失败必须记录真实原因、request id、call_type、provider、model、HTTP 状态或异常类型；日志不得包含 API Key。
11. 规则 / 模板降级可以用于维持游戏流程，但必须以明确 source / error 字段暴露，不能写成模型成功。

- `data/building_defs.json`

## 文档规则

每次改代码后检查是否需要更新：

- `CURRENT_STATE.md`
- `TASKS.md`
- `MODULE_INDEX.md`
- 对应模块文档
- `DEV_LOG.md`
- `CHANGELOG.md`

## 注释规则

注释解释“为什么”，不要重复“代码做了什么”。

好：

```gdscript
# 昏迷不等于死亡，保留 NPC 后续记忆和剧情反噬。
npc.unconscious = true
```

不好：

```gdscript
# 设置 unconscious 为 true
npc.unconscious = true
```
