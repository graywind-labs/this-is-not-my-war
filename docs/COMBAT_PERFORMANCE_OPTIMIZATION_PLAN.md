# 多人战斗性能优化方案

任务：T0396  
制定日期：2026-09-09  
状态：**Partial：已按玩家精确 GM 操作链完成第二轮 CPU / 渲染 / 物理单因素定位并保留有效项，仍未达到稳定 60 FPS**；结果与“不得无证据重复”台账见第 10、11 节。

## 1. 问题、目标与证据等级

用户反馈非战斗相对流畅，第三波及以后大量敌人进入战斗时严重卡顿。正式五波为 8 / 16 / 24 / 36 / 48 人；这是设计内容，优化须承受现有规模。

上一轮 Godot MCP 探查在当前 Main 中得到非战斗约 60 FPS、帧 P95 15.37 ms，第三波 24 人约 18 FPS、帧 P95 75.61 ms。后者敌人尚在远处，Draw Calls 约 9,725，接近非战斗约 9,800；Process P95 从 14.85 ms 上升至 63.12 ms，Physics P95 为 4.36 ms。该样本说明有明显的人数相关运行开销，但不是受控的完整因果实验：引擎 Process monitor 不能直接当作纯 GDScript 自耗时，须继续分项测量。

代码发现每物理帧每名敌人生成完整运动调试快照、组装嵌套 profile、深复制并反复解析装备和动画；已有状态签名去重被另一逐帧调用路径绕过。这些是可复核的重复工作，收益须实测。每个样本敌人存在多套动画/骨架节点，但节点存在不等于全部在求值，不能据节点计数直接删除骨架或动画。

第五波旧压力脚本复现异常位移；T0234 已记录实体胶囊拥挤。目标更新/pressure_repath 计数不等于引擎真实寻路耗时，不能凭计数认定主要瓶颈。上一轮的瞬时 FPS、旧隔离 CombatSystem P95、纯角色压力测试三者不可混为 Main 全场性能结论。

目标机器当前为 i7-12700F + RTX 4060 Ti、Godot 4.6.2。首要目标是玩家常用 1280×720 全站/近战视角、正式渲染器、1×战斗时间下 48 敌 + 8 NPC 的稳定 60 FPS；预热后帧 P95 ≤16.67 ms、P99 ≤25 ms、>33.3 ms 长帧占比 <1%。非战斗也须留出余量，目标 P95 ≤12 ms。目标是验收标准，不是提前承诺测量结果；未达到须给出真实余量与后续瓶颈。

## 2. 机制不变合同

以下不调整：

- 敌人数、兵种构成、刷波时点、出生规则、HP、攻防、穿透、速度、射程、攻击间隔、硬直和目标优先级。
- TimeSystem 时间倍率与暂停规则；逻辑 tick、逐敌轮转、接触采样和已有 AI 频率。
- 敌我碰撞层、形状尺寸、NavigationMap、RVO 与物理频率；不关闭屏外模拟，不把寻路失败伪装到达。
- 攻击序号、抬手/命中/恢复时间线、武器骨骼接触、箭矢/弩矢轨迹、伤害与死亡/昏迷/复苏、掉落、胜负。
- NPC 征召、指令、战术、逃离、记忆/见闻、资源、建筑、LLM 调用及费用；不增加真实 API 测试费用。
- 现有动作、装备外观、布娃娃、尸体停留、骑乘/落马、音频与大招效果的可见规则。

特别约束：近战命中读取真实动画武器变换，表现层不是天然与玩法无关。动画状态跳转、骨骼更新频率和不可见时停播均必须视为行为敏感；只做等值计算消除，不以动画 LOD 偷改命中结果。

## 3. 修改策略与工程保护

先登记 T0396 与本方案，再增加诊断和测试，获得优化前基线后改生产热点。当前工作树含大量已有修改；按本轮文件内容保存精确基线，仅回滚本轮对应片段，禁止 reset/checkout 整个工作树。每批只改一个成本来源，满足门槛后再叠加下一批。配置和权威源的哈希用于证明本轮冻结范围未被修改。

缓存必须有完整键和失效条件：首次初始化、ID/装备/HP/行动/骑乘/攻击序号/阶段变化、重建、清敌和重新开局。所有要连续读取的时间/速度字段仍实时同步；禁止只以 action 字符串为键导致同动作新一击不播放。暂停/恢复、同帧清理后重建、多个 NPC 与敌人共享脚本也须覆盖。

不引入 ECS、多线程战斗权威、全局对象池或通用缓存框架，不大规模重写 CombatSystem。避免对外 API/存档 schema 变更；新接口是只读轻量 getter 或显式 debug_*。

## 4. 阶段 P0：可重复基线与观测

1. 验证 MCP 指向当前工程并记录引擎/渲染器/分辨率/相机/时间倍率。MCP 断连按 AGENTS.md 报告并停止受影响工作；服务端/插件版本不一致不擅自升级。
2. 增加可开关的有限采样诊断，默认关闭；按真实帧采集时间分布，不在热路径每帧 print、不生成巨大快照。GM 提供开始/结果/停止入口，仅读取性能，不负责刷波或伤害。
3. 可复用 Main 基准从正式场景与正式 spawn_wave 构建 0/1/3/5 波场景，固定 seed、昼夜、相机、窗口与时间倍率；避免真实 LLM 在测量期间介入。预热与生成尖峰单独记录，采样必须验证敌人数、暂停状态和战斗仍在推进。
4. 分开报告：真实墙钟帧间隔、引擎 process/physics/navigation、渲染 draw calls/图元、节点/内存，以及 CombatSystem 表现同步/暂停同步/投射物/逻辑 tick 分项。分项可能嵌套，不能相加推断总时间。
5. headless 用于确定性合同与热点对照；GPU 窗口运行用于帧率目标。不能用 await process_frame 的 16.6ms 睡眠平台证明 CPU 耗时≤16.6ms。
6. 优化前先运行相关旧回归，记录原有失败。每次性能对比保持同一模式；先短采定位，收口进行至少三次有效重复或明确未完成部分。禁止同时跑两个重型性能进程污染样本。

## 5. 阶段 P1：等值消除重复工作（优先实施）

### P1-A 运动表现轻量读取

为 ActorMotionBody 提供只读的实时半径/基础速度访问，替换表现位移采样里仅为两个标量生成的完整 debug 快照。保留原调试接口、速度/位移/可见补偿公式与执行频率。验证 getter 与原 snapshot 值相等；相同输入下可见位移、转向、步态输出一致。

### P1-B 角色表现状态去重

通过分项测量确定完整 profile 应用占比。只消除语义未变化的装备/动画状态工作，连续的攻击时钟和步态速度仍更新。优先在现有角色接口内做精确等值短路，以覆盖敌人和既有调用者，避免两套不一致的缓存。

完整 profile 发生真实改变时立即应用；逐帧 movement 若只改变速度，更新播放速度即可，只有移动激活、步/跑、状态或动作片段变化才重新解析装备可见性。保留 transient 受击结束、同动作新攻击序号、暂停/恢复及攻击 one-shot 最终姿势。若实际收益有限，不为节省小常数引入难维护的跨系统引用缓存。

### P1-C 按实测扩展的只读消费优化

如分项显示音频/VFX/UI 正在为少量字段请求完整角色/战斗快照，可添加对应精简只读投影或复用本帧已有结果。必须保持消费频率、事件顺序、返回事实和生命周期；不得直接更改事件生成或丢弃合法反馈。

每小步门槛：解析通过、专属等值/生命周期验证通过、相关攻击/步态回归无新增失败，且相同模式热点成本稳定降低。否则回滚该步或明确修正。

### P1-D 实测定位后的引导区等值查询消除（P0 后细化，实施前登记）

P0 发现第五波敌军 AI 平均约 39 ms；其中逐敌攻击位约 2.81 ms、目标选择约 1.84 ms。当前 T0243 已使用动态引导区，不是旧独占槽位：目标存在判断无论预览返回“可达”还是“不可达”都返回 true，却为每名敌人穷举全部候选做验路。可在目标合法且使用引导区时直接返回 true；真正选定引导区的 `_ensure_enemy_guided_attack_position` 仍保留原排序和可达性检查。完整机会预览接口保留供诊断/其他调用者使用；查询拒绝计数只反映实际执行的查询。

占区统计当前对每个候选重新读取所有敌人的世界位置、查节点、读取/复制相同物理 profile。改为仅在一次同步选点调用的开头构建只读 body 列表，候选循环共享这一列表；函数无 await，期间无移动/伤害提交，因此同一次调用中事实等值。列表不跨调用/帧保存，下一名敌人决策立即重读真实世界，消除缓存失效风险。圆柱包含关系、排除自身、存活判定、名单排序、最近可达区和 tie-break 全部保持。

专项以旧逐候选算法作独立对照，覆盖远程多排、步骑混合、圆边界/高度、移入移出、死亡移除、目标不可达；同时跑 T0243 和攻击时间线，禁止借机调参或降决策频率。

### P1-E 索敌只读投影（P1-D 后细化，实施前登记）

分项显示第三波逐敌候选组仍需约 0.78 ms（Windows 样本），其中 NPC 查询占主要部分。现有索敌为获得名字与“是否有主武器”复制整份 NPC 档案；行为模式查询还构建完整移动进度快照。BuildingSystem.get_building 为名字/HP 同时计算维修、升级、可用性和各活动效率。

在各权威系统内增加只读最小投影：NPC 战斗身份、当前行为模式、建筑战斗身份/HP；不向调用者返回内部可变引用。`can_npc_act` 内部直接读取同一状态字典，保留全部原条件，避免在纯谓词内深复制。CombatSystem 优先消费这些接口，保留旧接口兼容 fixture；旧完整快照继续供 UI、存档和诊断使用。专属测试逐字段对照原输出，并覆盖 HP/装备/逃离/昏迷/深睡锁的同帧改变。无新缓存，不改判定顺序、时点或频率。

### P1-D2 占区查询局部空间索引（实战 P95 定位后、实施前登记）

门前 48 人自然交战、破门后转仓库的 15 秒样本发现攻击位选择 P95 6.49 ms/敌、整帧 P95 110.95 ms。仓库远程多排候选仍逐个扫描所有 48 个 body。对同一次同步查询已读取的 body 列表建立局部 4m XZ 网格，记录最大 body 半径；候选只查询半径覆盖的网格，并向四周额外扩一整格作为保守边界余量。精确圆柱距离/高度检查继续用原函数，occupant 名单仍排序，不以网格代替最终判定。网格同样不跨调用保存，不减少 AI 工作频率。专项对照完整扫描，覆盖负坐标、格边界、较大半径、高度、移出/死亡与实际步骑组合；若输出不等或没有收益，不保留。

### P1-F 通用 NPC 状态信号的相关性去重（玩家精确 GM 复测后登记）

玩家的实际复现链不是旧基准的“直接远距刷波”，而是 GM“一键征召&配装”8 人后调用近门 `debug_spawn_wave(3, false, true)`。该链进入密集交战后帧 P50/P95 约 `79/121 ms`，友军 AI 平均约 `29 ms`。单因素测量确认：友军攻击计时每步为 8 人分别调用 `update_npc_state`，每次都同步广播通用 `npc_state_changed`；单次广播约 `4.3 ms`，其中建筑功能灯约 `2.3 ms`、ActionSystem 约 `1.4 ms`。建筑灯在每个攻击计时字段变化时重复扫描全部建筑/全部 NPC 并调用整组地面装饰；ActionSystem 在没有对应待执行动作/治疗工作时仍做完整状态检查和延后清理。这些消费者不依赖攻击冷却、抬手经过时间等字段。

实现只在消费者内消除不相关重活，不改变 `NPCSystem.update_npc_state` 的写入、角色节点刷新、广播次数或同步顺序：建筑功能灯保存每名 NPC 的占用签名（位置、逃离、睡眠事实），只有签名变化才 `_refresh_all`；首次/重建/时间/建筑变化仍完整刷新。ActionSystem 先读取同一权威状态；昏迷/逃离继续走原完整清理，存在本 NPC 待执行动作、导航失败、治疗/建筑协作关系时继续走原流程，只有所有相关工作集均为空的正常 NPC 才快速返回。专项必须逐分支比较优化前后调用计数与最终状态，覆盖入伍战斗计时、位置/睡眠、昏迷/逃离、待执行动作、导航失败、治疗复苏和重建，不以节流或延迟改变事件语义。

## 6. 阶段 P2：渲染与动画专项（实测触发）

若 P1 后仍未达标，进一步分离脚本、动画、CPU 渲染提交、GPU、阴影、多视口与 UI 成本。特别检查隐藏 UI 的 SubViewport 是否仍重绘世界，以及角色是否真的有重复播放的动画实例。使用单因素临时 A/B，实验开关只留在测试夹具，不进入玩家流程。

可在证据充分时实施：隐藏面板停止其专属 Viewport 重绘；同一共享资源的等值复用；没有消费者的重复动画播放器停用；静态、同材质、同可见/损毁层级的装饰批处理。每项均须独立验证正面/侧面、昼夜、室内显隐、选中/血条、建筑损毁、镜头拉近拉远和重新开启。

不得盲目合并全部网格、删除 source skeleton/retarget、关闭阴影或减少粒子来达标。静态合批不得跨屋顶显隐、升级、损毁、材质变化或选择边界。动画烘焙/LOD 若需要改资产或改变近战接触精度，应另行形成精确方案后再实施；本轮优先修复纯冗余成本。

## 7. 阶段 P3：行为敏感项隔离

T0234 实体拥堵继续作为独立缺陷；本性能任务不通过放宽断言、降低 RVO 安全或限制物理速度掩盖它。仅当分项证据证明寻路是剩余主要成本时，先区分相同请求重复提交与真实动态目标更新。可以消除完全相同且导航拓扑未变化的重复只读计算；不得降低真实重寻路/AI 频率，因为这会影响接敌、追击、命中与平衡。

如需要改变寻路策略、碰撞恢复或目标预测，必须给出固定输入轨迹、动态目标/拥挤/门/骑兵测试与差异解释，登记独立任务。当前“游戏机制不变”约束不授权随意调参。

优先复用：T0133 战斗表现/尸体，T0236 步态，T0141 角色复用，T0142 攻击时间线，T0185 表现时间合同，T0186 交战稳定，A5-P2 第五波压力，五波胜利/主厅失败与 Main 启动。根据实际改动增加必要的等值测试，而不是照抄实现写断言。

性能通过需要：同条件优化前后原始结果可查、实际帧预算通过、机制回归无新增失败。只有热点变快但 Main 未达标时，记录“阶段完成/整体 Partial”，继续定位，不能把 headless/局部成绩替代全场目标。

## 9. 风险、回滚与交付

主要风险为缓存漏失效、动画 one-shot/受击恢复失步、骨骼接触与伤害不一致、清理后旧引用，以及测量工具自身开销。用精确比较、保持连续字段更新、默认关闭诊断、有限样本、现有攻击测试和清理复测控制风险。

任何新增玩法差异、视觉明显退化、错误或有效样本持续慢于基线，都停止叠加下一项，修复或回退本轮对应片段。旧失败须明确保留来源，不能当作新优化通过的证明。不给“零 bug”保证；交付可复现证据、已覆盖范围和真实剩余风险。

交付包含本方案及执行记录、针对性代码、可复用性能/回归入口、GM 使用说明，并同步 CURRENT_STATE、TASKS、MODULE_INDEX、COMBAT_SYSTEM、DEV_LOG；架构/版本文档按实际改动更新。正常验证不发送真实 LLM 请求。

### 11.1 台账维护规则

- 后续每次性能实验，无论成立、不成立、因机制/画质被否决，均必须在本节补充：精确夹具、原始数据文件、关键指标、是否进入生产、回滚状态和允许重访条件。
- `撤回/无收益` 方向只有在引擎版本、资产结构、渲染架构或复现夹具发生实质变化，或新的 profiler 证据直接指向它时才允许重访；重访必须先写明与本次证据不同之处。
- `诊断成立、生产禁用` 不能出现在发布配置，也不能计入最终 FPS 成绩。它只用于建立成本上下界和决定下一项安全设计。
- 所有性能结论都绑定硬件、分辨率、相机、人数、交战阶段和提交版本。不同夹具只可作线索，不能直接计算百分比或覆盖本台账。

## 12. 当前专业结论与下一阶段门槛

现版本已把玩家精确第三波路径从约 67ms 降至约 37.5ms，但 17–18ms 的物理底座加约 9ms 战斗逻辑意味着继续做零碎表现微调无法可靠达到 60 FPS。下一步应单独建立“密集角色物理/查询时序等值重构”任务：锁步录制第三波角色 Transform、接触对、攻击位、命中、伤害和建筑 HP；先把直接空间查询迁到允许并行物理的安全同步边界，再比较单线程/独立物理线程，或设计保持碰撞输出一致的接触代理。没有这套等值回放前，不启用独立物理线程、不改碰撞层/RVO/physics tick。

该阶段属于较高回归风险的架构优化，仍须保持 24 敌 + 8 NPC、所有碰撞/避障/攻击/伤害机制与事件顺序；如果无法证明等值，任务继续 Partial，而不是用降频、少算人或关闭画面达标。
