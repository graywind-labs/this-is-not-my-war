# Backend Schemas

T0306 keeps the existing `EventSummary.details: dict[str, Any]` contract. Godot may place deterministic aggregation metadata there for five high-frequency combat event types (`event_count`, damage totals, first/last time, first/final/minimum HP, and terminal flags). The schema and Model Adapter preserve that dictionary; they do not aggregate raw events or alter authoritative records.

T0116 adds `PlannedDialogueIntent`, `DialogueIntentRevalidationRequest`, and `DialogueIntentRevalidationResponse`. The planned item must exactly match the current hour in the 24-item plan and be `talk_to_npc` or `seek_guard_officer`. Only `modify` may return a non-empty changed `dialogue_goal`; `continue` and `cancel_and_replan` must leave it empty.

T0106 changes `EventSummary` from an original-event carrier into a compact provider-facing projection. Current callers send `type`, deterministic `summary`, `importance`, optional `day/time`, and optional decision-relevant `details`; raw `payload` is no longer a schema field. `event_id` remains accepted only for legacy fixture/audit compatibility and is omitted by current Godot and provider projections. `ShortTermMemoryContext` still separates all current-index experienced and witnessed records, while reflection events additionally preserve `memory_kind`.

T0070 requires every `StationResidentContext` entry to include strict `recruited` and `in_station` booleans. `StationSceneContext.resident_roster` now contains all registered NPCs; departed NPCs remain present with `in_station=false`, so callers must not infer either flag from list membership.

T0601 creates Pydantic models for backend AI request and response payloads. These schemas are data contracts only; they do not call a real model and do not perform game authority changes.

Current schema groups:

- `common.py`: shared game time, request metadata, NPC context, memory summaries and action candidates.
- `npc_ai.py`: dialogue, dialogue/action-failure plan-revision judgement, daily plan, selected-hour plan revision, battle judgement, daily reflection, knowledge graph update, proactive intention and player strategy classification payloads.
- T0095 makes `DailyReflectionRequest.summary_window` and `reflection_period` required. The window is exactly 21:00 to the next 21:00 and carries the authoritative `接到守备命令的第N天` label plus the public notice basis `我们奉命守住此地`; the period bounds the unsummarized snapshot range. These are narrative constraints only—Godot remains authoritative for sleep eligibility, watermark rotation and diary persistence.
- `StationSceneContext` is the single top-level world-context block for station-aware requests. It requires a setting summary plus non-empty resident, building, work-mode action, five-item public basic-resource and station-rule lists. Public resources are exactly grain, meal, wood, stone and iron; per-request allowed actions/decisions and runtime systems remain authoritative.
- T0067 requires `NPCStateContext` to preserve the Godot-supplied `behavior_mode`, `combat_mode`, `combat_strategy`, `morale_boost` and `escape_intent` fields. They are read-only context; the backend cannot apply modes, buffs or movement.

T0025 plan contracts:

- `PlanActionKind` is shared from `common.py`; current plan-capable kinds include work, eat, drink, sleep, train, pray, visit, chat, targeted assists, seek-guard intent, avoid / escape intent and idle.
- `ActionCandidate.action_kind` identifies the exact internal kind allowed for that candidate. T0097 keeps `PlanItem` as the stable backend/Godot response but gives the provider a smaller decision shape: `hour + action_id`, plus `location_id` for visits, `target_npc_id` for NPC targets, or `building_id` for building assists. Model Adapter discards all other item fields and compiles the exact candidate kind, location, internal target and priority before Pydantic response validation.
- A fixed/no-target action ignores provider-supplied target or location noise. A target-driven action must supply its behavior-specific selector and match `allowed_actions`; generic legacy `target_id` cannot substitute for the required selector. The compiled `PlanItem` must still preserve the exact internal action, kind, target and location combination.
- `PlanItem.dialogue_goal` carries a short opening request for `talk_to_npc` and `seek_guard_officer`.
- `PlanRevisionJudgementRequest` branches on `trigger_kind` and inherits the same station-aware character context used by planning and revision. Both branches carry `station_context`, `npc` (including current order, short-term memory and `long_term_memory={knowledge_graph, diary}`), allowed actions, current building/resource states and baseline `current_plan`; `dialogue` adds the completed conversation and session metadata, while `action_failure` adds the authoritative failed item, type/summary/context and work-count constraints. `required_revision_hours` is a sorted non-past hard subset that every successful response must include; autonomous NPC-NPC initiators and NPC-initiated `seek_guard_officer` sessions use it to require the ending current hour. The HTTP layer authoritatively unions any model omission and reports `required_revision_hours_authoritative_union` in `model_normalizations`; it does not choose the revised action. `plan_item_superseded` represents a pending daily-plan action replaced before it becomes an ordinary same-day cross-hour carryover; `action_completed` represents a successfully consumed action whose current hour needs a different follow-up activity. `PlanRevisionJudgementResponse.revision_hours` may be empty only when no required hour exists and no stage needs revision, while `needs_revision` must match whether the array is non-empty. The old `DialoguePlanRevisionJudgement*` names remain compatibility aliases.
- `PlanRevisionRequest` carries structured failure context, work-count constraints, `revision_scope=selected_hours`, a non-empty sorted `revision_hours` array, past work count and the remaining-work minimum. `PlanRevisionResponse.revised_items` must cover exactly those requested hours—no omissions, additions or duplicates.
- For `dialogue_kind=npc_npc`, business validation requires `replyer_id` to equal the requested target NPC and `response_kind=reply_to_npc`; player and escape-intervention requests require `reply_to_player`.

T0603 dialogue contract:

- `NPCDialogueRequest` is centered on the target NPC: `npc_id`, `npc_name`, `npc_setting`, `npc_state`, `short_memory`, `long_memory` and `location_context`.
- T0094 adds optional target-private `interrupted_activity_context`, captured by Godot only when the guard officer's first effective message actually interrupts the target. It distinguishes the real activity before interruption, the current plan item, and the tentative post-dialogue resume item. It is transient request context—not an event, memory, or authority change—and lets a sleeping NPC say it was just awakened and expects to resume sleep when the plan is unchanged.
- T0041 requires a non-empty `allowed_actions` list on every dialogue request. Godot builds it with the same dynamic candidate function used by daily planning; dialogue treats it only as the target NPC's capability boundary and never as an executed plan.
- `NPCIdentity` and dialogue `npc_setting` carry the concise stable `religion` together with personality, desires, fears, boundaries, and the broad `speech_style`. T0061 removed fixed `signature_lines` examples; T0100 adds `religion` without treating it as a replacement for personality, memories, or runtime facts.
- The current speaker is described separately with `speaker_name`, `speaker_text` and observable-only `speaker_context`; the guard officer's display name is always `守备官`. `speaker_context.state` must be empty, and legacy `speaker_npc` accepts only `null`, so another NPC's memory/order/location context cannot enter the replyer's request.
- `dialogue_state.visibility` is `private` or `local_public`; this only guides Godot event routing and does not let the backend write memory. T1201 adds `interaction_context` and `battlefield_context` for wartime dialogue.
- T0029 adds `dialogue_phase`: an NPC-NPC `invitation` uses `current_round=0` and asks the target to accept or reject before Godot interrupts either participant. T0030 makes `conversation` start at round 1 without a hard cap: `max_rounds=0` is the no-limit sentinel, while `soft_round_threshold` and non-empty `soft_round_guidance` tell the model when to end naturally.
- T0087 splits dialogue output into `PlayerNPCDialogueResponse`, `NPCNPCDialogueResponse` and `EscapeInterventionDialogueResponse`; each forbids extra fields. Recruitment uses only `recruitment_result`, NPC-NPC lifecycle uses `invitation_result` and `should_end_dialogue`, and escape intervention uses `escape_intervention_result=stay|leave`. The removed generic `intent` is not accepted.
- HTTP business validation ties the selected response model, rounds, recruitment request, avoid-combat reactions and armed-recruited wartime reactions to the request context. A schema-valid but context-invalid model output is recorded as invalid rather than silently applied.

Authority boundary:

- Godot remains responsible for HP, resources, movement, building state, combat damage and event writes.
- Backend schemas describe NPC intent, text, subjective judgement, plan suggestions and memory/reflection output.
- Any text visible to NPCs should refer to the player as `守备官`; stable IDs may use `guard_officer`.
